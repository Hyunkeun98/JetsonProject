# 파일 재생(`jetson-replay`)과 임계값 추천(`jetson-threshold`) 설계

- 작성일: 2026-10-07
- 상태: 사용자가 대화로 설계 승인, 구현 요청 (스펙 문서 별도 검토는 구현 후 리뷰에서 함께 확인)

## 1. 목적

수집해 둔 DX1 JSON 파일로 (a) 모델을 학습하고 (b) 구간별 점수를 내고 (c) 알람 임계값을
추천한다. 설비를 다시 돌리지 않고, MQTT 브로커 없이 쓴다. 운영 경로(DX1 → 브로커 → 앱)는
바뀌지 않는다. 점수 계산은 운영 앱과 같은 부품을 쓴다.

성공 기준
- run1으로 학습 → 점수 → 추천이 끝까지 된다.
- 같은 데이터를 앱 처리기(`SnapshotProcessor`)와 재생 루프에 넣으면 점수가 같다(테스트).
- 정상 데이터만 있을 때와 이상 데이터가 있을 때 모두 추천한다.

비목표: 앱의 MQTT 수신 경로 검증, 데이터 기록 기능, 설정 파일 자동 수정, 그룹별 임계값
(앱은 임계값 하나만 쓴다).

## 2. 구성

```
jetson-replay train      파일 → 학습 구간 → 모델 저장 (+ 상태 마커 MONITORING)
jetson-replay score      파일 + 모델 → 검증/이상 구간 점수 CSV
jetson-threshold         점수 CSV → 임계값 후보 표 + 추천 (+ report.json)
```

모듈: `segments.py`(구간 파일), `replay.py`(파일 읽기·학습·점수), `threshold.py`(후보 계산·추천),
`replay_cli.py`, `threshold_cli.py`. 모두 앱과 같은 설정 YAML(`load_equipment_config`)을 읽는다.

## 3. 입력

- **데이터 폴더**: `*.json`, `*.jsonl`을 모두 읽는다. 한 줄이 DX1 메시지 하나(`{"records":[...]}`)다.
  토픽 이름은 쓰지 않고, 앱처럼 `config.tags`에 있는 태그만 고른다(`parse_and_filter_records`).
  레코드는 이벤트 시각 순으로 정렬한다.
- **구간 파일**(`segments.yaml`):
  ```yaml
  train:        [{start: "2026-10-02T11:15:00+09:00", end: "2026-10-02T11:32:50+09:00"}]
  normal_eval:  [{start: "...", end: "..."}]
  anomaly:      [{name: servo_touch_1, start: "...", end: "..."}]
  ```
  - 시각은 시간대(`Z` 또는 `±hh:mm`)가 반드시 있어야 한다. 없으면 오류.
  - 구간은 `[start, end)`, `start < end`.
  - 서로 다른 구간(종류 불문)이 겹치면 오류. 학습과 검증이 겹치면 오탐이 적게 나와 임계값이 낮게
    추천되기 때문이다.
  - `train`은 `train` 명령에서만, `normal_eval`/`anomaly`는 `score` 명령에서 하나 이상 필요하다.
  - 이상 구간 이름은 중복될 수 없다. 생략하면 `anomaly_<번호>`.

## 4. 재생 규칙

- 구간마다 `EventTimeResampler`를 새로 만들어 그 구간의 레코드만 넣는다. 구간 사이를 이어 붙인
  윈도우를 만들지 않는다. (구간 끝의 지연 허용 시간만큼은 확정되지 않아 버려진다.)
- **학습**: 학습 구간들의 스텝을 `CalibrationSample`로 바꿔 `make_train_fn`(앱과 같은 학습 함수)에
  넘긴다. 구간 경계의 윈도우 몇 개는 이어 붙은 상태로 학습되지만, 앱의 캘리브레이션 버퍼도 통신
  공백을 이어 붙이므로 같은 수준이다. 학습 후 `<model-dir>/<id>.state`를 `MONITORING`으로 써서
  앱이 같은 `--model-dir`로 바로 이어서 쓸 수 있게 한다.
- **점수**: 구간마다 `SlidingWindow` + `InferenceEngine`으로 스텝마다 앱과 같은 순서(윈도우로
  예측 → 점수 → 스냅샷 push)로 계산한다. 리셋(`step.reset_window`, 구간 시작)은 다음에 나오는 점수
  행의 `reset=1`로 기록한다. 점수가 None인 스텝은 행을 만들지 않는다(앱도 이때 디바운서를 갱신하지
  않는다).
- 모델/설정 불일치는 앱의 호환성 검사와 같은 기준으로 중단한다.

## 5. 점수 CSV

열: `epoch_ns, time(UTC ISO), kind(normal_eval|anomaly), segment, reset, <그룹>_score, <그룹>_top ...`.
그룹은 모델의 그룹 구성(없으면 `all`). 임계값 분석은 이 파일만 읽는다.

## 6. 임계값 계산

앱의 알람은 그룹마다 "점수 ≥ 임계값이 `confirm`번 연속"이고 전체 알람은 그룹 알람의 OR이다.
행을 `reset`으로 끊은 연속 구간에서 길이 `confirm`인 창의 최솟값을 구하고 그 최댓값을
**임계 점수(c)**라 하면, 임계값 T에서 알람이 한 번이라도 나는 조건은 `T ≤ c`와 같다.

- 구간별 c(그룹별 c의 최댓값이 구간 c). 창이 만들어지지 않으면 c = -∞.
- `normal_c` = 정상 구간 c의 최댓값 → 오탐 0건이 되는 최소 임계값 `T0` = `normal_c`를 0.1 단위로
  올린 값(최소 2.0으로 제한: `MIN_THRESHOLD`).
- 이상 구간 a는 `T ≤ c_a`에서 검출된다. 모두 검출하는 최대 임계값 `T1 = min_a c_a`를 0.1 단위로
  내린 값.
- 후보 표(기본 격자 2,3,4,5,6,8,10,12,15,20,30; `--grid`로 변경)는 임계값마다 시뮬레이션으로
  정상 알람 건수(연속 알람은 1건), 24시간당 건수(정상 구간 첫~끝 행 시간 합), 이상 검출 수,
  검출까지 걸린 시간(구간 첫 점수 행 기준)을 낸다. 그룹별 `T0`도 같이 낸다.
- `confirm`은 `--confirm 3,5,10`으로 여러 개를 줄 수 있고, 값마다 표와 추천을 낸다. 기본은 설정의
  `alarm.confirm_steps`(`--config`가 없으면 3).

추천 규칙
- 이상 구간이 없을 때: `T0 × margin`(기본 1.2, `--margin`)을 0.1 단위로 올린 값. "민감도 미검증",
  정상 검증 구간 길이를 함께 표시한다. `--max-alarms-per-day N`이 있으면 시뮬레이션에서 그 건수
  이하가 되는 가장 낮은 후보를 추천한다(여유 없음).
- 이상 구간이 있을 때: `T0 ≤ T1`이면 `(T0+T1)/2`(0.1 단위)를 추천한다. `T0 > T1`이면 하나의
  임계값으로 정상 오탐 0건과 전부 검출을 동시에 만족할 수 없으므로 추천하지 않고, `T0`에서의 검출
  수와 놓치는 구간을 보여 준다.
- 이상 구간 수가 3개 미만이면 "표본이 적어 과적합 위험" 경고를 붙인다.
- 정상 검증 구간이 없으면 오류로 중단한다.

출력: 화면 표와 `--report`(기본 `threshold_report.json`). 설정 파일은 고치지 않는다.

## 7. 오류 처리

시간대 없음, 구간 겹침, 데이터 폴더/파일 없음, 구간 안에 스텝이 없음, 모델 없음, 모델/설정 불일치,
점수 CSV 형식 오류는 원인을 적어 종료 코드 2로 중단한다. 학습 구간의 스텝 수가
`calibration.min_samples`보다 적으면 경고한다(중단하지 않음).

## 8. 테스트

- 구간 파일: 정상 파싱, 시간대 누락, `start >= end`, 겹침, 중복 이름, 종류별 필수 검사.
- 파일 읽기: 태그 필터, 구간 필터, 정렬, 깨진 줄 무시.
- 앱과의 일치: 같은 스텝을 `SnapshotProcessor`(기록용 발행기)와 재생 루프에 넣어 점수 일치.
- 임계값: 임계 점수 c가 시뮬레이션과 일치(여러 `confirm`, reset 경계), 추천 규칙(정상만/이상 포함/
  충돌/표본 경고), 건수·시간 계산.
- CLI: 합성 JSON으로 train → score → threshold를 끝까지.
- 마지막에 run1 실제 데이터로 기존 MQTT 재생 결과와 비교한다.
