## 배경: 실제 DX1 데이터로 확인된 사실

`C:\WORK\10. Jetson\Data\Actuator_1.json`, `Axis_Status_3.json` — 실제 DX1이 내보내는 JSON 포맷 샘플. 확인된 특징:

- **설비 하나에 다중 토픽**: 같은 물리 설비 안에 여러 공정이 있고, 공정별 서보모터 값/설비 전체 actuator 값이 서로 다른 PLC Collector → 서로 다른 MQTT 토픽으로 나뉘어 들어온다. 확인된 것 외에 약 9개 토픽이 더 있다(총 11개 내외). 이상탐지는 이 전부를 종합해서 판단해야 한다.
- **태그명 규칙**: `PLC_Collector_<Collector명>:<신호명>` (예: `PLC_Collector_Actuator_1:AirBlower.Cmd[0]`, `PLC_Collector_Axis_Status_3:AxCV_VelDemVal`). 상위 문서의 `component:tag` 가정과 다르지만 여전히 `문자열:문자열` 형태라 기존 config의 `tags` 목록 방식은 그대로 유효하다.
- **이진값과 연속값이 혼재**: `Actuator_1`은 전부 0/1 디지털 신호(Cmd/Sensor), `Axis_Status_3`는 속도값(TargetVel/VelDemVal) 같은 연속값을 포함한다.
- **샘플링 주기 ~30ms**(초당 30회 이상) — 상위 문서 예시의 `1s`보다 훨씬 빠르다.
- **PLC 내부 카운터로 보이는 필드 존재** (`AxCV_PosTimestamp` 등, 예: `13591692046567`) — 실제 물리량이 아니라 스캔 카운터로 판단, 기본적으로 분석 대상에서 제외.
- 확보한 샘플은 약 1초 구간(30~35개 레코드)뿐이라 모든 태그 값이 정지 상태였다 — 동적 패턴 검증에는 더 길고 실제 가동 중인 데이터가 필요하다 (하단 "미해결" 참고).

## 1. Config 구조 개정 (상위 문서 3절 대체) ✅ 완료

```yaml
equipment_id: "line_A"
mqtt:
  subscribe_topics:                      # 단수 -> 복수
    - "dx1/line_A/actuator_1"
    - "dx1/line_A/axis_status_3"
    # ... 설비당 최대 11개 내외, 개수 제한 없음
  publish_topic: "jetson/line_A/anomaly"
tags:
  - "PLC_Collector_Actuator_1:AirBlower.Cmd[0]"
  - "PLC_Collector_Axis_Status_3:AxCV_VelDemVal"
  # PLC 카운터류(PosTimestamp 등)는 여기 적지 않으면 자동으로 분석 제외.
  # 나중에 필요해지면 이 목록에 추가하기만 하면 됨 (코드 변경 불필요).
resample_interval_ms: 50                 # 기본값. 설비 특성에 맞게 조정 가능
window_size: 100                         # 기본 5초치 히스토리. 공정 사이클 길이 확인되면 재조정 권장
calibration:
  max_duration: "7d"                     # 이 이상 지난 캘리브레이션 데이터는 정리
  min_samples: 10000                     # 미달 시 학습 명령 거부
```

**태그 타입(이진/연속) 자동 판별**: config에 타입을 적지 않는다. 캘리브레이션 데이터에서 태그의 관측값이 전부 `{0, 1}`이면 이진, 아니면 연속으로 학습 시점에 자동 분류한다. 태그가 수십~백 개 규모로 늘어날 걸 감안한 결정.

## 2. Tag Buffer (수집 파이프라인) ✅ 완료

- MQTT 구독 스레드가 **여러 토픽을 동시 구독**, 수신되는 모든 태그의 "최신값"을 하나의 스레드세이프 딕셔너리에 갱신 (태그명 자체에 Collector명이 포함돼 있어 토픽이 여러 개여도 이름 충돌 없음)
- 별도 주기 스레드가 `resample_interval_ms`마다 깨어나 그 시점 스냅샷(모든 config 등록 태그의 최신값, 짧은 결측은 ffill)을 만듦
- `window_size`개 쌓인 슬라이딩 윈도우가 모델 입력 1건

이 부분은 상위 문서 1절 아키텍처의 "Tag Buffer" 컴포넌트를 그대로 따르되, 다중 토픽을 반영한 구체화다.

## 3. 캘리브레이션 데이터 저장 ✅ 완료

수동 트리거 방식(4절 참고)이라 학습 명령이 언제 올지 알 수 없다. `CALIBRATING` 상태 동안:

- 리샘플된 스냅샷을 메모리에 무한정 쌓지 않고 **설비별 파일에 순차 append**(예: `calibration_buffer.parquet`) — Jetson이 재시작돼도 이어서 쌓인다
- `calibration.max_duration`(기본 7일)을 넘는 오래된 데이터는 정리해서 무한정 커지는 것을 방지
- 학습 명령이 오면 그 시점까지의 파일을 읽어 학습 → 성공하면 파일 삭제(모델 가중치+통계만 남김) → `MONITORING` 전환
- `calibration.min_samples` 미달 시 학습 명령을 에러로 거부하고 `CALIBRATING` 유지

## 4. 캘리브레이션 트리거 (상위 문서 4절 개정) ✅ 완료

**자동(기간/샘플 수 기반) 전환을 폐기하고, 사람이 명시적으로 트리거하는 방식으로 바꾼다.** 명령은 두 가지로 나뉜다 (상위 문서 4절의 `recalibrate` 명령을 아래처럼 구체화):

- **`train`**: 지금까지 `CALIBRATING` 상태에서 쌓인 캘리브레이션 버퍼로 학습을 실행한다. 설비가 정상 가동 중임을 사람이 육안으로 확인한 뒤 보낸다. `min_samples` 미달이면 거부(3절), 충족하면 학습 → `MONITORING` 전환.
- **`recalibrate`**: `MONITORING` 상태를 `CALIBRATING`으로 되돌리고 **캘리브레이션 버퍼를 비운 뒤 새로 데이터 수집을 시작**한다. 정비/부품 교체 등으로 "정상 기준" 자체가 바뀌었을 때 사용. 이후 다시 `train` 명령을 보내야 새 모델로 전환된다.
- **모니터링 중 자동 온라인 재학습은 하지 않는다** (상위 문서 4절에서 이미 결정한 원칙 유지 — 서서히 진행되는 실제 고장 전조를 "새 정상"으로 잘못 학습해버릴 위험 때문). 모델 갱신은 오직 사람이 `train`을 명시적으로 보낼 때만 일어난다.

## 5. 모델 구조 ✅ 완료

**PyTorch GRU 1개** (설비당 통합 모델 — 태그 개별 모델 대비 관리 부담이 작고, 태그 간 상관관계도 학습에 반영됨). 입력은 `window_size × 태그수` 정규화 시퀀스, 출력은 "다음 시점 모든 태그 값" 예측.

- **연속 태그**: 캘리브레이션 데이터 기준 z-score 정규화 → 회귀 head → MSE
- **이진 태그**: 정규화 없이 0/1 그대로 → 시그모이드 head(다음 시점 1일 확률) → BCE
- 학습 손실 = (연속 태그 MSE 평균) + (이진 태그 BCE 평균) — 둘 다 정규화된 스케일이라 가중치 조정 없이 합산

**학습 시 저장하는 것**: 모델 가중치, 연속 태그별 정규화 통계(평균/표준편차), 태그별 타입 판별 결과, 태그별 "정상 오차 분포" 통계(평균/표준편차 — 아래 6절에서 사용).

## 6. 실시간 이상 점수 계산 ⬜ 미착수 (다음 서브프로젝트: 실시간 추론 통합)

매 스텝:

1. 현재 윈도우로 다음 시점 값 예측 (연속: 값, 이진: 확률)
2. 실제 값 도착 시 태그별 원본 오차 계산 — 연속: `|실제 z-score - 예측 z-score|`, 이진: `|실제(0/1) - 예측확률|`
3. 이 원본 오차를 **그 태그의 캘리브레이션 구간 "평소 오차" 평균/표준편차**로 재정규화: `(원본오차 - 평소오차평균) / 평소오차표준편차` → 태그별 최종 z-score
4. **모든 태그의 z-score 중 최댓값**을 그 시점의 이상 점수로 사용 (평균이 아닌 최댓값을 쓰는 이유: 태그가 수십~백 개 규모라 국소적 이상 — 액추에이터 하나만 고장 — 이 평균에 희석되는 것을 방지. 어떤 태그가 최댓값을 냈는지가 Phase 2 기여도 분석에 그대로 재사용됨)
5. **디바운스**: 순간적 노이즈로 인한 오탐을 줄이기 위해, 이상 점수가 임계값을 **연속 N틱(기본 3틱 = 150ms) 이상** 넘어야 알람을 확정한다. 1틱짜리 튐은 무시.

## 7. 에러 처리 (상위 문서 5절에 추가) 🔶 부분 완료

- **학습 명령을 받았는데 `min_samples` 미달**: 명령을 거부하고 에러 메시지 반환, `CALIBRATING` 유지 — ✅ 완료
- **캘리브레이션 버퍼 파일 손상/읽기 실패**: 학습을 중단하고 에러 로그, 사람이 재캘리브레이션(버퍼 초기화 후 처음부터)을 판단하도록 알림 — ✅ 완료
- **모델 파일 손상/로드 실패**: 상위 문서 5절과 동일 — `MONITORING` 진입을 막고 `CALIBRATING`으로 폴백 — ⬜ 미착수 (Inference Engine이 없어 "MONITORING 진입" 자체가 아직 없음 — 6절과 함께 구현 예정)
- **다중 토픽 중 일부만 끊김**: 해당 토픽의 태그만 ffill 처리(상위 문서 5절 결측 정책과 동일), 나머지 토픽은 정상 처리 계속 — ✅ 완료 (Tag Buffer 구현에 포함)

## 8. 테스트 전략 🔶 부분 완료

상위 문서 6절의 "도루코 CSV 리플레이" 방식은 이제 실제 DX1 JSON 포맷(`records` 스키마)과 구조가 다르므로, **이 파이프라인 검증은 실제 DX1 JSON 샘플(`Actuator_1.json`, `Axis_Status_3.json` 및 향후 확보할 나머지 토픽 샘플)을 반복 재생하는 시뮬레이터**로 한다. 다만 현재 확보한 샘플은 정지 상태만 담고 있어 캘리브레이션 학습/이상탐지 로직 검증에는 부족하다 — 최소한 정상 가동 사이클이 여러 번 반복되는, 수 분~수십 분 분량의 동적 데이터가 필요하다(아래 미해결 항목).

파이프라인 메커니즘(리샘플링 정합성, 캘리브레이션 상태 전이, 디바운스 타이밍, 모델 저장/로드) 자체는 정지 상태 샘플로도 단위 테스트가 가능하다 — 실제 이상탐지 "정확도" 검증과는 별개로 먼저 진행할 수 있다.

> **진척**: 리샘플링/캘리브레이션 상태 전이/모델 저장·로드 단위 테스트는 ✅ 완료(87개, `jetson_app/tests/`). 디바운스 타이밍 테스트와 실제 이상탐지 정확도(동적 데이터 기반) 검증은 6절 구현 및 동적 캘리브레이션 샘플 확보 이후로 ⬜ 미착수.

## 미해결/추후 확정 필요 항목

- **동적 캘리브레이션용 샘플 데이터 확보**: 현재 샘플은 1초 정지 구간뿐 — 정상 가동 사이클이 반복되는 실제 데이터 필요
- **`window_size` 재조정**: 공정 하나의 사이클 시간(그리퍼가 잡고-놓는 데 걸리는 시간 등)을 알게 되면 `window_size`(기본 100스텝=5초)를 그 사이클 길이에 맞게 재조정하는 것을 권장
- **나머지 ~9개 토픽의 스키마**: 아직 미확인 — 확보되는 대로 태그명 규칙이 동일한지, 새로운 데이터 타입(문자열 상태값 등)이 있는지 확인 필요
- **디바운스 N틱, 임계값 k**: 기본값(3틱, k=3σ 등)은 실제 데이터로 튜닝 필요
- **PLC 카운터 필드의 향후 분석 방식**: 제외는 확정, 필요 시 어떻게 활용할지(예: 스캔 지연 탐지)는 미정
